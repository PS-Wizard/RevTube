# Video Audit

Async, LLM-scored audit of a channel's videos across six elements: **Title,
Description, Tags, Keywords, Thumbnail, Captions**. All text elements are scored
by DeepSeek. The **Thumbnail** element reuses the existing **Thumbnail Optimizer**
12-pillar Gemini analysis (`thumbnailOptimizerService.analyze`) instead of a
separate vision path, so both features share one audit engine. Jobs run on the
BullMQ `videoAudit` queue (see `backend/services/videoAuditService.js`).

## Scoring

- Each element is scored against admin-configured criteria (`config/auditCriteria`,
  `DEFAULT_AUDIT_CRITERIA.video`). Every criterion has a `weight` and an `element`.
- A criterion's LLM score is clamped to 0-10. Per-criterion `earned = score * weight`.
- **Element score** (0-100) = `round(Σ earned / Σ weight * 10)` across its criteria.
- **Video total** (0-100) = same weighted mean over every criterion.
- Niche-tagged criteria matching the channel niche get `weight * 1.5`.

## Thumbnail element (reuses Thumbnail Optimizer)

The thumbnail element does NOT run a separate Gemini Vision pass. Instead
`scoreVideo` calls the production `thumbnailOptimizerService.analyze()` once per
video, passing a watch URL built from `videoId`
(`https://www.youtube.com/watch?v=<id>`) plus the channel niche. It reuses the
first `ThumbnailAudit` result:

- **Element score** (0-100) = `clampScore(audit.currentScore) * 10` (the
  Thumbnail Optimizer's 0-10 `currentScore` mapped to the 0-100 element scale).
- **Fix target** for projections = `audit.expectedScore * 10` (the Optimizer's
  own projected uplift), surfaced as each recommendation's `targetPerElement`.
  This means the video-audit projection reflects real 12-pillar upside, not the
  generic `FIX_TARGET = 9`.

The full `ThumbnailAudit` (reviewSummary, strengths, opportunities,
`detailedAreas`, `currentScore`, `expectedScore`) is attached to the element as
`thumbnailAnalysis` so the UI can show it without a second call.

### Normal view vs. detailed child audit

- **Normal view** (Video Audit detailed breakdown): the thumbnail element shows
  only its score plus a **General Knowledge** summary (the Optimizer's
  `reviewSummary`) and a **"Detailed Thumbnail Analysis"** button. This keeps the
  video audit focused while still surfacing the headline verdict.
- **Detailed child audit**: runs persist their embedded child analyses into the
  Optimizer history as one `thumbnail_audits` row named "Video Audit -- <date>"
  (the row id travels back on the job result as `thumbnailAuditSavedId`), so the
  **"Detailed Thumbnail Analysis"** button prefers opening that saved entry:
  `/thumbnail-optimizer?audit=<rowId>&scroll=<videoId>` loads it via the page's
  normal `handleLoadAudit` path (no AI re-run), expands this video's deep-dive
  accordion (`thumb-audit-<videoId>` anchor), and smooth-scrolls it into view.
  Fallback when no saved row exists (legacy pre-persistence runs, or saving was
  skipped): navigates to `/thumbnail-optimizer?video=<id>&niche=<niche>&auto=1`;
  on mount the Thumbnail Optimizer page auto-enqueues the full 12-pillar audit
  for that single video (`handleSubmit` with the watch URL + niche), then renders
  the complete per-pillar deep dive. A running child audit survives page
  navigation via the same `useSessionJobId` sessionStorage persistence.

## Recommendations (projected uplift)

`scoreVideo` also returns a deterministic projection: if every weak criterion
(earned < `FIX_TARGET = 9`) were raised to the target, what would the video total
become? This projection is a math-only estimate and costs no extra LLM call.

- `projectedTotal` (0-100) = weighted mean with weak criteria lifted to the target.
  Never lower than the live `total`.
- `recommendations[]` = one entry per element whose fix lifts the video total
  by `>= MIN_RECO_DELTA = 1` point:
  - `element`, `current` (element score now), `projected` (element score if fixed),
  - `delta` (points added to the video total), `targetPerElement` (the fix target, 90).
- Sorted by `delta` descending. Computed with the exact same weighting math as the
  live score, so the "will get that much score if set" number is exact, not a guess.

The projection is a number only. The actual ready-to-use fixes (rewritten copy)
are in the separate `suggestions` field described below, generated by an
additional LLM call.

UI surfaces: the per-video accordion summary shows a `→ 84 (+12)` projected chip;
the detailed breakdown shows a "Fix to improve" tip per weak element with both the
projected point delta and the concrete suggestion when available; exports
(PDF/Excel/CSV) include the projected score.

## Concrete suggestions

On top of the numeric projection, `scoreVideo` can return real, ready-to-use
replacements for each weak element, not just a point delta. After the projection
is computed, if there is at least one recommendation and a DeepSeek JSON adapter
is wired in, the engine makes ONE additional DeepSeek JSON call per video
(`buildSuggestionPrompt` in `videoAuditService.js`, served by `deepSeekJson` in
`videoAuditLLM.js`). That call receives the video's current metadata and the list
of weak elements, and returns concrete copy keyed by element.

The response shape is `suggestions: { [element]: { ... } }` on each video result.
Each element key (only those that were weak and had data) holds an object of the
following form:

- `title` -> `{ options: ["alt title 1", "alt title 2", "alt title 3"], scores: [82, 74, 91], why: "short reason" }`
- `description` -> `{ rewrite: "a fuller, more helpful description", score: 88, why: "short reason" }`
- `tags` -> `{ suggested: ["tag1", "tag2"], scores: [70, 65], why: "short reason" }`
- `keywords` -> `{ suggested: ["keyword1", "keyword2"], scores: [68, 72], why: "short reason" }`
- `thumbnail` -> `{ concepts: ["concept 1", "concept 2"], why: "short reason" }`

Each **scored alternative** carries a 0-100 number produced by re-running the
SAME `deepSeekText` element scorer the live audit used, so the number is
directly comparable to the element's own score (e.g. 3 alt titles -> 3
independent title scores in `title.scores`, parallel to `title.options`).
`description.rewrite` gets a single `score` (it is one block of copy).
Thumbnail `concepts` are intentionally **not** scored -- a concept cannot be
scored without a generated image. These `scores`/`score` fields are what the
detailed UI renders as a pill next to each alternative.

The suggestion prompt enforces a mandatory **quality bar**: every alternative
must itself be strong enough to score >= 80/100 on its element (genuinely
click-worthy titles, 15-20 high-volume + long-tail tags, 10-15 real keyword
phrases, an engaging description rewrite). As a safety net, the UI only renders
alternatives whose scored value is >= `MIN_ALT_SCORE` (80); genuinely weak
filler is hidden rather than shown as a low number.

The `why` field explains the rationale for the suggestion. Not every element
appears in every response, only the weak ones that had data.

Graceful degradation: if `DEEPSEEK_API_KEY` is unset, the adapter returns null, and
if the call throws or parses to garbage, the catch falls back to an empty object.
In either case the audit still returns all scores and the projection, and only the
`suggestions` field is empty. No scores are lost when suggestions are unavailable.

## No-data exclusion

Some elements have no input data on a given video. A video with no captions yields
criteria marked `note: "no data"` with `max: 0`, and the grouped element gets
`hasData: false` (`videoAuditService.js`). Such absent elements are now excluded
from two places:

- The **projected total computation**: a no-data element contributes its current
  (zero) earned value unchanged, so it neither raises nor lowers the projection.
- The **recommendations list**: an element with `hasData` false is never pushed as
  a fixable item.

This fixes the previous contradiction where a missing element displayed
"Raise this element from 0 to 90 and the video gains +90 pts", since there was
nothing to raise. Absent elements are never recommended as fixable, and because
they have no data they also never appear in `suggestions`.

## API

- `POST /video-audit` enqueue `{ channelId, videoIds }` -> `{ jobId }`
- `GET /video-audit/jobs/:id` poll state + `result`
- `POST /video-audit/history` save, `GET /video-audit/history`, `GET /video-audit/history/:id`, `DELETE /video-audit/history/:id`
- `GET /video-audit/history/by-video/:videoId` -> `{ id: number | null }` — newest saved audit whose `results[].videoId` matches; powers the Optimized Content **View Audit** deep-link (`/video-audit?audit=<id>&scroll=<videoId>` loads the entry via `handleLoadAudit` and scrolls to that video's accordion, no AI re-run)

When a run finishes, the user is notified (in-app bell, email, and an OS
notification if the tab is backgrounded) -- see [Notification System](../13-Notification System/02-Notification Reference).
The `jobId` is persisted in `sessionStorage` via `useSessionJobId`, so leaving the
page or closing the tab never cancels the server-side job; returning resumes polling.
